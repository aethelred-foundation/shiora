# Shiora — Compliance Control Matrix & Gap-to-Production Roadmap

> **Status: testnet-preview.** This document is the _honest_ record of Shiora's
> compliance posture. It maps each required control to the **actual code or
> process that implements it today**, and marks truthfully what is not yet
> real. It exists so that no one — internally, in a pilot, or in investor
> diligence — mistakes an aspirational claim for an operational control.
>
> Certification status: **None of HIPAA, SOC 2, HITRUST, or ISO 27001 is
> certified.** Those are auditor- and time-gated and cannot be produced by
> code. This document is the evidence base an auditor would start from.
>
> **The structured assurance deliverables built on top of this matrix** — the
> HIPAA risk assessment, BAA template + subprocessor register, penetration-test
> scope, SOC 2 readiness assessment, and SaMD classification analysis — live in
> [`docs/compliance/`](compliance/README.md).

## Legend

| Mark               | Meaning                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------- |
| ✅ **Implemented** | Real, tested control present in the codebase today.                                           |
| 🟡 **Partial**     | Real control exists but is incomplete for production (e.g. in-memory only, dev-key fallback). |
| ⛔ **Not started** | Claimed elsewhere but **no real implementation exists yet**.                                  |
| 📋 **Process**     | Non-code control requiring human/legal/operational action.                                    |

## 1. HIPAA Security Rule — Technical Safeguards (§164.312)

| Control                                           | Requirement                     | Status         | Evidence / Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------- | ------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C-ENC-1** Encryption at rest                    | §164.312(a)(2)(iv), (e)(2)(ii)  | ✅ Implemented | `src/lib/crypto/envelope.ts` — AES-256-GCM envelope encryption, per-record DEKs wrapped by a KEK, AAD context binding, tamper detection. Tested in `src/__tests__/lib/crypto/envelope.test.ts`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **C-ENC-2** Key custody                           | Keys held in a KMS/HSM, rotated | 🟡 Partial     | Custody sits behind two seams: `KeyProvider` (`src/lib/crypto/key-provider.ts`, Vault KV-backed KEK for staging) and `DekWrapper` (`src/lib/crypto/dek-wrapper.ts`). **Vault Transit DEK wrapping is implemented and adopted through the entire PHI envelope path** (envelope → both encrypted repositories → re-seal job → IPFS service; selected via `SHIORA_TRANSIT_KEY_NAME` + Vault addr/token; the master key never enters application memory). Versioned rotation with mixed-custody reads and a batched re-seal/migration job (docs/KEY_MANAGEMENT.md). **Gap:** production Vault Transit rollout (real Vault deployment, scoped token policy) and removing the env-key path in production. |
| **C-ENC-3** Encryption in transit                 | §164.312(e)(1)                  | 🟡 Partial     | TLS terminated at the platform edge; HSTS gated behind `SHIORA_ENABLE_HSTS`. **Gap:** enable HSTS + preload, enforce TLS 1.2+ ciphers, mTLS for service-to-service.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **C-ENC-4** Client-side / end-to-end encryption   | Stated in SECURITY.md           | ⛔ Not started | The README/SECURITY claim "encrypted before leaving the browser" is **not yet implemented**. Either build browser-side sealing (VALORA wallet key) or correct the claim.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **C-AUTH-1** Authentication                       | §164.312(d)                     | ✅ Implemented | `src/lib/api/wallet-verify.ts` — real secp256k1 ECDSA + bech32 address derivation; `src/lib/api/session.ts` — HMAC-SHA256 signed, `__Host-` cookies, timing-safe compare.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **C-AUTH-2** MFA                                  | Best practice / HITRUST         | 🟡 Partial     | TOTP (RFC 6238) implemented — `src/lib/api/totp.ts` + `mfa-service.ts` + `/api/mfa*`; secret sealed at rest, audited. **Gap:** step-up enforcement on sensitive actions (enrolment/verification primitives are done).                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **C-AC-1** Access control / authorization         | §164.312(a)(1)                  | ✅ Implemented | `requireAuth` gates routes; data is owner-scoped at the repository layer. **Role-based access control is implemented**: `src/lib/api/rbac.ts` + `capabilities.ts` + `roles.ts` + `roles-service.ts` define a 6-role capability matrix (individual / provider / employer_admin / payer_analyst / government / researcher), and provider record access additionally requires an **active, unexpired** grant (`view_granted_records`). **Remaining:** a documented joiner/mover/leaver authorization _procedure_ (📋 process).                                                                                                                                                                         |
| **C-AC-2** Automatic logoff                       | §164.312(a)(2)(iii)             | ✅ Implemented | Session TTL (`SHIORA_SESSION_TTL_HOURS`) enforced in `verifySessionToken`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **C-AUD-1** Audit controls                        | §164.312(b)                     | ✅ Implemented | `src/lib/api/audit-log.ts` — `PersistentAuditLog` writes a **durable**, owner-/subject-scoped audit trail over a backing store (`src/lib/persistence/audit-store.ts` / `pg-audit-store.ts`), surviving restart. Self-scoped activity feed (`/api/me/activity`) and subject-side disclosure log (`/api/me/access-log`, §164.528). **Remaining:** centralized log aggregation / SIEM export (📋 ops).                                                                                                                                                                                                                                                                                                 |
| **C-AUD-2** Audit integrity                       | §164.312(c)(1)                  | ✅ Implemented | `src/lib/crypto/audit-chain.ts` — SHA-256 hash-linked, append-only chain; `verifyAuditChain` detects edits, deletions, reordering. Tested.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **C-AUD-3** Audit durability + anchoring          | Tamper-_proofing_               | 🟡 Partial     | Durable, concurrency-safe append implemented: the Postgres `audit_chain` store advances the chain head via a `seq` PRIMARY KEY with insert-and-retry, so concurrent multi-process appends cannot fork or overwrite the chain (`src/lib/persistence/pg-audit-store.ts`; verified against a real Postgres engine). **Gap:** mirror the chain to a WORM/object-lock sink and anchor the head hash on the Aethelred L1 so a single operator cannot rewrite history.                                                                                                                                                                                                                                     |
| **C-INT-1** Integrity of PHI                      | §164.312(c)(1)                  | ✅ Implemented | GCM auth tags (envelope) + audit-chain hashing both detect unauthorized alteration.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **C-NET-1** Transmission security / rate limiting | §164.312(e)(1)                  | 🟡 Partial     | `src/lib/api/middleware.ts` — CORS origin enforcement + rate limiting; **distributed limiter implemented** (`src/lib/persistence/pg-rate-limiter.ts` — atomic windowed counter, multi-process safe; in-memory limiter for dev). **Gap:** WAF + bot/DDoS protection at the edge; TLS floor + HSTS (see C-ENC-3).                                                                                                                                                                                                                                                                                                                                                                                     |

## 2. Data Plane & Infrastructure (gaps that block real PHI)

| Control                                    | Status                            | Gap                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------ | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C-DB-1** Durable encrypted datastore     | ✅ Implemented                    | Real ports-and-adapters datastore: every PHI-bearing entity is sealed via `EncryptedDocumentRepository` / `EncryptedRecordRepository` over **Postgres** when `DATABASE_URL` is set (in-memory only outside production; `datastore-mode.ts` **throws** in production without a DB so the in-memory store never holds PHI). Versioned migrations (`migrator.ts`). The legacy flat-file mock store is removed. **Remaining:** managed backups / PITR (📋 ops).                                                                                                         |
| **C-TEE-1** Confidential compute           | ⛔ Not started (hardware-gated)   | `teeVerified: true` is **hardcoded**; no attestation is performed. Honestly labeled `simulated` in the maturity registry. A _real_ SGX/TDX/SEV-SNP/Nitro quote cannot be produced in software — it requires the hardware + a vendor attestation service. The buildable-now half is an attestation-document **verifier**; the generation side is genuinely external.                                                                                                                                                                                                 |
| **C-ZK-1** Zero-knowledge proofs           | ✅ Implemented                    | **Real, transparent-setup** non-interactive ZK set-membership proofs: a Cramer–Damgård–Schoenmakers OR-proof over the RFC 3526 3072-bit prime, domain-separated Fiat–Shamir (`src/lib/crypto/zk-membership.ts`). `/api/zkp/prove` produces genuine proofs; `/api/zkp/verify` is publicly verifiable; the proven value and blinding are never stored. No trusted setup / toxic waste. **Scope:** binding commitments to issuer-attested attributes (anonymous credentials) is the trust layer above.                                                                 |
| **C-INF-1** Health assistant (SANA)        | 🟡 Partial (real, non-diagnostic) | SANA is engineered to be non-diagnostic: input screening intercepts emergencies/crises without invoking the remote service, a hard non-diagnostic instruction contract, and output screening + mandatory disclaimer (`src/lib/api/sana/guardrails.ts`). The operator-managed inference gateway is mandatory and missing configuration fails closed. Conversations are encrypted, owner-scoped, and included in the GDPR lifecycle. Not a medical device (see [SAMD_ASSESSMENT.md](compliance/SAMD_ASSESSMENT.md)). **Remaining:** verifiable-inference attestation. |
| **C-MPC-1** Secure multi-party computation | ✅ Implemented                    | **Real secure aggregation** over a (t, n) Shamir secret-sharing scheme (`src/lib/crypto/secret-sharing.ts`): contributions are secret-shared, summed via the additive homomorphism, and only the aggregate (sum/mean/count) is reconstructed and stored — individual inputs are never persisted. `/api/mpc/sessions` (researcher-gated). **Scope:** true input privacy additionally requires non-colluding parties (the platform retains only the aggregate).                                                                                                       |
| **C-IPFS-1** Content-addressed storage     | ✅ Implemented                    | **Real, spec-compliant CIDv1** content addressing (`src/lib/crypto/cid.ts`, verified against the canonical IPFS empty-file vector). Upload **encrypts then addresses** (the CID addresses ciphertext, never plaintext PHI); resolution re-derives the CID for tamper-evidence before decrypting. Pluggable store: local content-addressed node by default, any Kubo-compatible HTTP node/pinning gateway when `IPFS_API_URL` is set.                                                                                                                                |

## Honest current-posture statement (use this language externally)

> Shiora is in **testnet-preview**. Its authentication boundary and PHI
> encryption/audit-integrity primitives are real and tested; its data plane,
> confidential-compute and managed inference integrations are in development and currently
> operate on synthetic data. Shiora is **designed for** HIPAA and GDPR and is
> **not yet certified**. Compliance certifications and any clinical/regulatory
> clearances are in progress.

This replaces non-substantiated present-tense claims ("HIPAA compliant",
"processing occurs exclusively inside TEE", "encrypted before leaving the
browser") in `README.md`, `SECURITY.md`, and the marketing site until the
corresponding ⛔/🟡 controls reach ✅.

## Roadmap to "production-ready for real PHI" (sequence)

1. **Backbone.** ✅ envelope encryption, ✅ audit-chain integrity, ✅ durable **Postgres** datastore (replaced the flat-file mock), ✅ durable concurrency-safe audit. **Remaining:** move KEK to **KMS** (C-ENC-2); L1-anchor the audit head (C-AUD-3).
2. **Identity & authorization.** ✅ RBAC for the six audience roles (C-AC-1); 🟡 MFA primitives (C-AUTH-2) — step-up enforcement remaining.
3. **Real integrations.** ✅ Zero-knowledge proofs (C-ZK-1), ✅ secure MPC (C-MPC-1), ✅ content-addressed storage (C-IPFS-1), ✅ non-diagnostic health assistant (C-INF-1). **Remaining:** TEE attestation (C-TEE-1, hardware-gated), FHIR R4, verifiable-inference attestation.
4. **Hardening.** ✅ distributed rate limiting (C-NET-1) → **Remaining:** WAF, HSTS/TLS floor (C-ENC-3), client-side encryption (C-ENC-4), external pen test (see [PENETRATION_TEST_PLAN.md](compliance/PENETRATION_TEST_PLAN.md)).
5. **Compliance & regulatory (parallel, human-gated).** ✅ risk assessment, BAA template + register, SOC 2 readiness, SaMD analysis authored ([`docs/compliance/`](compliance/README.md)). **Remaining (third-party):** executed BAAs, written policies, a SOC 2 / HITRUST examination, and a SaMD determination by counsel.
6. **Per-audience verticals** built on the audited backbone.
