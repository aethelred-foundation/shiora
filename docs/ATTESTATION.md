# Shiora — Hardware Attestation Verification

Status: **real, cryptographically-enforced verification** for AMD SEV-SNP,
100% covered (`src/lib/attestation/`). This closes the "TEE was a claim, not a
capability" gap (formerly EXT-3 in `TECHNOLOGY_GAP_ASSESSMENT.md`) by _building_
the verifier rather than removing the surface.

## What this is

A confidential-compute attestation proves that a specific, measured enclave —
not a rogue process or a leaked key — produced a result. For sovereign,
regulated health workloads (M42/G42-class), "our clinical AI runs in a verified
enclave" is only credible if the platform can _cryptographically verify_ the
enclave's attestation, without trusting Shiora's own servers. This subsystem
does exactly that.

It replaces the trust model of the legacy `contracts/core/ShioraTEEVerifier`
(which _self-signs_ attestations with an operator key) and the unverified
`bytes32 attestation` field on `ShioraConsentManager`: those bottom out in
"trust this key/hash." Here, trust bottoms out in the **vendor's silicon root of
trust** (AMD's ARK), enforced by public-key cryptography.

## The trust model (vendor-neutral)

```
   pinned vendor root (AMD ARK)      ← trusted by pinning, at deploy time
        │ issues
   intermediate (AMD ASK)
        │ issues
   endorsement key cert (VCEK)       ← certifies the enclave's signing key
        │ signs
   ATTESTATION_REPORT                ← carries { measurement, report_data(nonce) }
```

Verification (`verifyAttestation`) proves, in order, and **fails closed** on any
failure:

1. **Trust root is pinned.** No pinned root for the platform → `no-trust-root`.
   Roots are supplied explicitly by the operator (`registerTrustRoot` or
   `SHIORA_ATTEST_ROOT_AMD_SEV_SNP`), never fetched implicitly.
2. **Cert chain is valid.** Each certificate is signed by the next
   (`X509Certificate.verify`), inside its validity window, terminating at the
   pinned root. Uses only Node's built-in `X509Certificate` — no third-party
   ASN.1/PKI library in the trust path.
3. **Report signature is genuine.** The SEV-SNP `ATTESTATION_REPORT` (real
   fixed 1184-byte layout) is verified with ECDSA-P384/SHA-384 against the VCEK
   public key (the chain leaf). Signature bytes are the report's little-endian
   `r‖s` fields, converted to IEEE-P1363 for `crypto.verify`.
4. **Freshness is bound.** The report's `report_data` must begin with the
   caller's expected nonce → defeats replay of an old quote.
5. **Measurement is allowed.** When the policy pins an allowlist of known-good
   enclave measurements, the report's launch measurement must be one of them.

A pass yields `{ verified: true, measurement, reportData, trustRootFingerprint }`
and a stable `attestationReference()` (a SHA-256 over platform ‖ measurement ‖
report_data ‖ root) suitable for storing on a record or anchoring on-chain via
`ShioraSealAttestation`. There is **no path** to `verified: true` without every
check passing — never a fabricated badge.

## What is real vs. what is next (honest boundary)

- **Real now:** the full trust model and cryptography — X.509 chain
  verification, the SEV-SNP report parser, ECDSA-P384 signature verification,
  nonce and measurement binding, fail-closed defaults. Production-usable against
  a real AMD SEV-SNP quote once the operator pins AMD's published ARK.
- **Adapters next (`adapter-pending`):** Intel SGX (DCAP), Intel TDX, and AWS
  Nitro each have a different quote/report byte format. Their parsers are the
  documented next adapters; they reuse the same verified core (cert chain,
  report signature, nonce, and measurement checks). Until an adapter lands, that
  platform rejects honestly as `adapter-pending` — never silently verified.
- **Hardware boundary:** _generating_ a live quote requires provisioned
  confidential-compute hardware (an SEV-SNP host) at deploy time — an operator
  provisioning step, not a code gap. This subsystem _verifies_ quotes; it does
  not manufacture silicon. The verification logic is complete and correct today.

## Operating it

- Pin the vendor root at deploy: `SHIORA_ATTEST_ROOT_AMD_SEV_SNP=<AMD ARK PEM>`
  (or call `registerTrustRoot('amd-sev-snp', pem)` from bootstrap). With no root
  pinned, SEV-SNP verification fails closed.
- Verify a document:

  ```ts
  import { verifyAttestation } from '@/lib/attestation';

  const result = verifyAttestation(
    { platform: 'amd-sev-snp', report: base64Report, certChainPem: vcekThenAsk },
    { expectedNonce: requestNonceHex, allowedMeasurements: knownGoodImages },
  );
  if (result.verified) {
    // anchor result via attestationReference(result) / ShioraSealAttestation
  }
  ```

## Tests

`src/__tests__/lib/attestation/attestation.test.ts` — 30 tests, **100%
statements/branches/functions/lines**. A real ECDSA-P384 test PKI
(ARK→ASK→VCEK, generated by `scripts/gen-attestation-test-pki.sh`) signs
layout-exact synthetic reports; the suite proves the pass path plus every
failure branch: no-trust-root, adapter-pending, malformed report/chain,
untrusted chain, expiry, not-yet-valid, tampered body, wrong signing key,
nonce mismatch, measurement-not-allowed. Test fixtures are clearly test-only;
production pins the real vendor root.
